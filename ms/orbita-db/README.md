# ORBITA DB: восстановление структуры

Восстановленная структура находится в `database/recovery/2026_10_14_000000_reconstruct_legacy_schema.php`.
Это отдельный, явно запускаемый набор Laravel migrations для новой базы после потери старой. Он создаёт 50 таблиц. Обычные служебные миграции `orbita_*` остаются в `database/migrations`, без изменений.

## Источники и точность

Сопоставлены:

- 39 CSV из `/Users/Shared/SharedProject/БД/orbitadb-csv`: 11 непустых, 28 пустых; всего 8 043 строки, включая 49 строк журнала миграций и 19 строк password_resets.
- Все 49 имён миграций из `migrations.csv` найдены в `/Users/evgenijcelnokov/Work/DEVOPS/DB/MAIN-DB/database/migrations`.
- Модели и morph map в `/Users/evgenijcelnokov/Work/BACKEND/CRUD/CRUD-LH-2023-2/src/app` и текущем `ms/orbita-api/app/Modules/Catalog`.

Архив `MAIN-DB-2023` использует UUID и не соответствует числовым ID выгрузки. Использована более ранняя версия `MAIN-DB`. Миграция самодостаточна и не требует этих архивных директорий при запуске.

`database/recovery-manifest.json` фиксирует источник, порядок колонок и наличие CSV для каждой таблицы. Непустые CSV подтверждают порядок и совместимость полей, но не доказывают точное совпадение прежних типов, индексов, defaults, FK, views или triggers. Для пустых и отсутствующих CSV схема восстановлена по архиву. Это реконструкция, а не подтверждённый schema-only экспорт production.

## Связи и принятые решения

- Имена таблиц сохранены, преимущественно в единственном числе.
- Числовые `id` с автоинкрементом сохранены по архиву: unsigned integer для сущностей, unsigned bigint для системных таблиц. Это глобальный ID таблицы, не отдельная последовательность на каждый `key`.
- `parentable_type` (nullable string) + `parentable_id` (nullable unsigned bigint) создаются явно через `nullableNumericMorphs`, независимо от глобальных UUID-настроек Laravel. Составной индекс не уникален: один родитель может иметь множество дочерних записей. Внешний ключ на одну таблицу здесь невозможен.
- Для таблиц с `key` и полиморфным родителем добавлен неуникальный индекс `(key, parentable_type, parentable_id)` под запросы проекта.
- `key` — строка длиной 36, совместимая со старым MySQL `uuid`/CHAR(36). В CSV встречаются `1` и `2`; оба сохраняются. Default изменён с архивного `base` на `1` для текущего проекта. Это осознанное решение реконструкции, не доказанный старый default. У таблицы `key` нет одноимённой колонки согласно архиву.
- `price.value` — `DECIMAL(20,2)` вместо архивного INTEGER: все выгруженные цены целые (0–400222432), а текущий код поддерживает копейки. Float/double не используются. Это осознанное расширение схемы.
- Nullable timestamps, deleted_at, поля slug/hash/alt и особые структуры `users`, `cart`, `jobs`, токенов сохранены по архиву. Cart не превращается в полиморфную таблицу: архив содержит product_id и session_user.
- На slug и полиморфные пары не добавлены уникальные ограничения. Наличие `morphOne` в некоторых моделях не доказывает уникальность данных; миграция не мешает восстановить несколько дочерних строк.
- Типы в CSV — короткие morph aliases (`product`, `category` и т. д.). При импорте их нельзя заменять PHP-именами классов. Morph map настраивается приложением, не DDL.

CSV отсутствуют для `users`, `unit`, `text`, `team`, `title`, `service`, `seotitle`, `video`, `tag`, `visit`, `technology`. Их таблицы создаются пустыми. Пустые `menu`/`project` и отсутствующие другие родители означают, что создание схемы само по себе не восстановит целостность каталога. `taggables` и `action` из более позднего архива не включены: их нет ни в журнале этой базы, ни в CSV.

## Запуск на новой базе

В `orbita-db` нет отдельного Laravel runtime: используется Artisan соседнего `orbita-api`, как и для существующих служебных миграций.

1. Создать отдельную пустую MySQL-базу и настроить подключение `orbita-api` именно к ней. Проверить DB_URL и кэш конфигурации: они могут переопределять переменные подключения.
2. Из `ms/orbita-api` выполнить:

```sh
php artisan migrate --path=../orbita-db/database/recovery
```

3. При необходимости создать таблицы текущего приложения отдельным запуском:

```sh
php artisan migrate --path=../orbita-db/database/migrations
```

Artisan использует журнал `orbita_migrations` согласно конфигурации API. Таблица `migrations`, создаваемая восстановлением, предназначена только для старого журнала. Не переключать Laravel на этот старый журнал и не выдавать его содержимое за историю новых миграций.

Перед первым CREATE проверяется отсутствие **всех** 50 целевых таблиц. Если любая уже существует, восстановление останавливается, ничего не создавая. MySQL DDL не атомарен: при ошибке посередине останется частичная схема; повторный запуск откажет, и нужно разобраться с причиной на отдельной новой базе. `down()` удаляет только эти 50 legacy-таблиц в обратном порядке и уничтожает их данные; служебные `orbita_*` не затрагивает.

Миграция создаёт только структуру: не импортирует CSV, не создаёт фиктивные товары/родителей, не включает каталоговые записи и не устанавливает schema approval. Запуск на реальной базе в рамках подготовки не выполнялся.

## Формат CSV и импорт данных

Файлы без заголовков: первая строка — данные. Порядок колонок указан в manifest. Это CSV с обратной косой чертой для экранирования кавычек; стандартное чтение без этого параметра ошибочно разбивает 164 строки product. SQL NULL представлен некавыченным `\N`.

Команда `orbita:recovery-import` зарегистрирована в `orbita-api`. Она читает manifest из соседнего `orbita-db`; в образе `orbita-db` manifest находится в `/recovery-manifest.json`, а recovery-миграция — в `/recovery`. Образ API, на котором собран образ DB, должен содержать новую команду.

Из `ms/orbita-api` сначала выполнить проверку только файлов (без подключения к БД):

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv --dry-run
```

Исходная выгрузка содержит **17 конфликтов ID изображений**: одинаковым ID соответствуют разные строки. По умолчанию команда выводит их номера записей в `id_conflicts`, завершает проверку с кодом 1 и отказывает в импорте. Для сохранения всех изображений предусмотрена явная опция:

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv \
  --dry-run --reassign-conflicting-image-ids > /tmp/orbita-recovery-plan.txt
```

Первая запись каждого ID сохраняется; следующие получают номера **выше максимального исходного ID image**, в порядке строк CSV. Пропускаются ID, на которые уже ссылаются строки CSV: потерянная ссылка не должна случайно начать указывать на новое чужое изображение. Соответствия `record / first_record / original_id / new_id` находятся в `id_reassignments`. Файлы не изменяются, строки не удаляются, остальные поля и ID других таблиц сохраняются. Если на конфликтующий ID ссылается импортируемая запись, встречается неизвестный morph alias или исчерпан диапазон ID, перенумерация отказывает. Конфликты ID других таблиц эта опция не разрешает.

Для данной выгрузки с опцией подготовлены 8 024 строки: 7 975 записей каталога и 49 записей архивного журнала `migrations`. 19 строк `password_resets` пропускаются. Команда всегда исключает `password_resets`, `personal_access_tokens`, `jobs`, `failed_jobs`, `cart`: старые токены, очередь и сессии не восстанавливаются. Исходные CSV и их значения в репозиторий не копируются.

### Проверка подключения и загрузка

1. Подготовить отдельную отключённую от приложения MySQL 8.0+/8.4 базу **`orbita_recovery_<имя>`**, направить подключение API на неё и выполнить recovery-миграцию по инструкции выше. Все другие процессы записи/очереди должны быть остановлены; `ORBITA_CATALOG_WRITES_ENABLED=false`. Проверить `DB_URL` и кэш конфигурации. Импортёр не создаёт базу/таблицы и не переключает подключение.
2. Проверить CSV и целевую схему без вставок, явно указав её точное имя (пример — `orbita_recovery_20261019`):

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv \
  --dry-run --target-database=orbita_recovery_20261019 \
  --reassign-conflicting-image-ids
```

3. После просмотра отчёта выполнить загрузку теми же параметрами без `--dry-run` и сохранить отчёт соответствий ID:

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv \
  --target-database=orbita_recovery_20261019 \
  --reassign-conflicting-image-ids > /tmp/orbita-recovery-import.txt
```

`--target-database` — проверка точного имени настроенной и реально подключённой базы, а не переключатель подключения. Допускаются только базы `orbita_recovery_*`, без префикса таблиц. SQLite `:memory:` доступен исключительно тестам. Обычные имена рабочих БД команда отвергает.

Перед вставкой проверяются все 50 таблиц, порядок колонок, отсутствие FK/представлений/триггеров, независимый auto-increment ID и InnoDB. Все legacy-таблицы должны быть пустыми; необязательные `orbita_*` service-таблицы тоже, кроме журнала `orbita_migrations`. Неизвестные таблицы запрещены. Нужен строгий SQL mode. Импортёр не дописывает, не заменяет, не чистит таблицы и не вызывает Eloquent events, сидеры или старые миграции.

CSV целиком проверяются до первой вставки: наличие всех ожидаемых файлов, точное количество строк из manifest, ширина строк, UTF-8, формат ID/дат/Decimal. Файлы без CSV по manifest остаются отсутствующими; неожиданно найденные файлы требуют предварительного пересмотра manifest. Снимок ограничен 32 MiB и 100 000 строк, CSV-симлинки запрещены. После разбора используется неизменяемый снимок в памяти; файлы не перечитываются во время загрузки. Отчёт содержит SHA-256 каждого файла и только служебные данные — без текстов товаров, email, токенов и SQL bindings.

Вставки выполняются пакетами в **одной транзакции**. Advisory lock исключает одновременный запуск другого recovery-импортёра; он не заменяет остановку внешних писателей. Ошибка вставки, предупреждение конвертации MySQL или несовпадение количества строк/MAX(id)/AUTO_INCREMENT откатывают все вставленные строки. Счётчики InnoDB могут продвинуться даже после rollback; команда проверяет следующий ID выше максимального восстановленного, не выполняя ALTER TABLE. Повторный успешный импорт запрещён из-за непустых таблиц.

`relationship_issues` содержит количество отсутствующих/неполных/неизвестных родителей, межпроектных ссылок, групп повторяющихся slug и неоднозначных morphOne-связей. Эти строки сохраняются как в выгрузке. На текущем снимке найдены 374 отсутствующих родителя, 1 неполная и 1 межпроектная связь, 15 групп повторяющихся slug товаров; их исправление — отдельная работа. Успешный импорт не означает целостный каталог: approval и обычные записи приложения остаются выключенными. Общий allocator впоследствии инициализируется штатной проверкой/утверждением схемы; импортёр его не обходит для работающего приложения и не создаёт approval.

`csv-profile.py` остаётся отдельной проверкой числа полей, а не импортёром.

## Проверки

Из корня ORBITA, при установленных зависимостях `orbita-api`:

```sh
php ms/orbita-db/tests/recovery.php
php ms/orbita-db/tests/mysql-grammar.php
python3 ms/orbita-db/tests/csv-profile.py /Users/Shared/SharedProject/БД/orbitadb-csv
python3 scripts/check-migrations.py
cd ms/orbita-api
php vendor/bin/phpunit --filter RecoveryImportTest
```

Первый тест использует только синтетические записи в SQLite `:memory:` и не читает `.env`: 50 таблиц, порядок колонок, неуникальные morph indexes, nullable parents, реальные Eloquent morphMany/morphTo, одинаковые ID разных типов родителей, проверка коллизии до DDL, rollback/reapply и сохранность служебной таблицы. Второй компилирует MySQL DDL с запретом реального подключения. Проверка CSV сопоставляет ширину всех 8 043 строк с manifest, не печатает значения ячеек.

`RecoveryImportTest` проверяет синтетические CSV и SQLite `:memory:`: NULL/пустые строки/escaping, повреждённые файлы, Decimal/даты/ID, отчёт по связям, перенумерацию image и запрет неоднозначных ссылок, пустую схему, повторный импорт, позднюю ошибку и rollback, отсутствие секретов в ошибках, регистрацию команды и dry-run без запросов к БД.

`tests/import-mysql.php` дополнительно проверен на отдельном временном MySQL 8.4: атомарный rollback после ранних успешных вставок, точные Decimal/текст/NULL/key, перенумерация image, AUTO_INCREMENT, отказ от повторного импорта и не-InnoDB. Скрипт использует только синтетические CSV, не читает `.env`, создаёт и удаляет собственную базу со случайным именем `orbita_recovery_test_*`. Запускать только с одноразовым MySQL, не публикуя порты:

```sh
docker run -d --rm --name orbita-recovery-mysql-test --network none \
  --tmpfs /var/lib/mysql:rw -e MYSQL_ALLOW_EMPTY_PASSWORD=yes mysql:8.4
# Дождаться готовности MySQL. PHP-образ должен содержать PDO MySQL и PHP >=8.4.
docker run --rm --network container:orbita-recovery-mysql-test \
  -e ORBITA_RECOVERY_MYSQL_TESTS=1 \
  -v "$PWD/ms/orbita-api:/workspace/ms/orbita-api:ro" \
  -v "$PWD/ms/orbita-db:/workspace/ms/orbita-db:ro" \
  -w /workspace/ms/orbita-api --entrypoint php larux/orbita-api:latest \
  ../orbita-db/tests/import-mysql.php
docker stop orbita-recovery-mysql-test
```

Docker-команды выполняются из корня ORBITA. Нужны установленные зависимости `orbita-api` в монтируемой директории. Импорт реальных данных в MySQL в рамках разработки не выполнялся; исходный CSV проверен файловым dry-run с явной перенумерацией image.
