# ORBITA DB: восстановление структуры

Восстановленная структура находится в `database/recovery/2026_10_14_000000_reconstruct_legacy_schema.php`.
Это отдельный, явно запускаемый набор Laravel migrations для новой базы после потери старой. Он создаёт 50 таблиц. Обычные служебные миграции `orbita_*` остаются в `database/migrations`, без изменений.

## Источники и точность

Сопоставлены:

- 39 CSV из `/Users/Shared/SharedProject/БД/orbitadb-csv`: 11 непустых, 28 пустых; всего 8 043 строки, включая 49 строк журнала миграций и 19 строк password_resets.
- Все 49 имён миграций из `migrations.csv` найдены в `/Users/evgenijcelnokov/Work/DEVOPS/DB/MAIN-DB/database/migrations`.
- Модели и morph map в `/Users/evgenijcelnokov/Work/BACKEND/CRUD/CRUD-LH-2023-2/src/app` и текущем `ms/orbita-api/app/Modules/Catalog`.

Архив `MAIN-DB-2023` использует UUID и не соответствует числовым ID выгрузки. Использована более ранняя версия `MAIN-DB`. Миграция самодостаточна и не требует этих архивных директорий при запуске.

`database/recovery-manifest.json` фиксирует источник, порядок колонок и наличие CSV для каждой таблицы. Непустые CSV подтверждают порядок и совместимость полей, но не доказывают точное совпадение прежних типов, индексов, defaults, FK, views или triggers. Для пустых и отсутствующих CSV схема восстановлена по архиву. Это реконструкция, а не подтверждённый schema-only экспорт production.

## Связи и принятые решения

- Имена таблиц сохранены, преимущественно в единственном числе.
- Числовые `id` с автоинкрементом сохранены по архиву: unsigned integer для сущностей, unsigned bigint для системных таблиц. Это глобальный ID таблицы, не отдельная последовательность на каждый `key`.
- `parentable_type` (nullable string) + `parentable_id` (nullable unsigned bigint) создаются явно через `nullableNumericMorphs`, независимо от глобальных UUID-настроек Laravel. Составной индекс не уникален: один родитель может иметь множество дочерних записей. Внешний ключ на одну таблицу здесь невозможен.
- Для таблиц с `key` и полиморфным родителем добавлен неуникальный индекс `(key, parentable_type, parentable_id)` под запросы проекта.
- `key` — строка длиной 36, совместимая со старым MySQL `uuid`/CHAR(36). В CSV встречаются `1` и `2`; оба сохраняются. Default изменён с архивного `base` на `1` для текущего проекта. Это осознанное решение реконструкции, не доказанный старый default. У таблицы `key` нет одноимённой колонки согласно архиву.
- `price.value` — `DECIMAL(20,2)` вместо архивного INTEGER: все выгруженные цены целые (0–400222432), а текущий код поддерживает копейки. Float/double не используются. Это осознанное расширение схемы.
- Nullable timestamps, deleted_at, поля slug/hash/alt и особые структуры `users`, `cart`, `jobs`, токенов сохранены по архиву. Cart не превращается в полиморфную таблицу: архив содержит product_id и session_user.
- На slug и полиморфные пары не добавлены уникальные ограничения. Наличие `morphOne` в некоторых моделях не доказывает уникальность данных; миграция не мешает восстановить несколько дочерних строк.
- Типы в CSV — короткие morph aliases (`product`, `category` и т. д.). При импорте их нельзя заменять PHP-именами классов. Morph map настраивается приложением, не DDL.

CSV отсутствуют для `users`, `unit`, `text`, `team`, `title`, `service`, `seotitle`, `video`, `tag`, `visit`, `technology`. Их таблицы создаются пустыми. Пустые `menu`/`project` и отсутствующие другие родители означают, что создание схемы само по себе не восстановит целостность каталога. `taggables` и `action` из более позднего архива не включены: их нет ни в журнале этой базы, ни в CSV.

## Запуск на новой базе

В `orbita-db` нет отдельного Laravel runtime: используется Artisan соседнего `orbita-api`, как и для существующих служебных миграций.

1. Создать отдельную пустую MySQL-базу и настроить подключение `orbita-api` именно к ней. Проверить DB_URL и кэш конфигурации: они могут переопределять переменные подключения.
2. Из `ms/orbita-api` выполнить:

```sh
php artisan migrate --path=../orbita-db/database/recovery
```

3. При необходимости создать таблицы текущего приложения отдельным запуском:

```sh
php artisan migrate --path=../orbita-db/database/migrations
```

Artisan использует журнал `orbita_migrations` согласно конфигурации API. Таблица `migrations`, создаваемая восстановлением, предназначена только для старого журнала. Не переключать Laravel на этот старый журнал и не выдавать его содержимое за историю новых миграций.

Перед первым CREATE проверяется отсутствие **всех** 50 целевых таблиц. Если любая уже существует, восстановление останавливается, ничего не создавая. MySQL DDL не атомарен: при ошибке посередине останется частичная схема; повторный запуск откажет, и нужно разобраться с причиной на отдельной новой базе. `down()` удаляет только эти 50 legacy-таблиц в обратном порядке и уничтожает их данные; служебные `orbita_*` не затрагивает.

Миграция создаёт только структуру: не импортирует CSV, не создаёт фиктивные товары/родителей, не включает каталоговые записи и не устанавливает schema approval. Запуск на реальной базе в рамках подготовки не выполнялся.

## Формат CSV и последующий импорт

Файлы без заголовков: первая строка — данные. Порядок колонок указан в manifest. Это CSV с обратной косой чертой для экранирования кавычек; стандартное чтение без этого параметра ошибочно разбивает 164 строки product. SQL NULL представлен некавыченным `\N`.

Будущий импорт должен корректно декодировать MySQL NULL и escape-последовательности, сохранять id/key/aliases, явно перечислять колонки и проверить потерянных родителей, дубликаты и счётчики ID. `csv-profile.py` проверяет только число полей и **не является импортёром**. Не следует слепо импортировать старые токены/сбросы паролей. Исходные CSV и их значения в репозиторий не копируются.

## Проверки

Из корня ORBITA, при установленных зависимостях `orbita-api`:

```sh
php ms/orbita-db/tests/recovery.php
php ms/orbita-db/tests/mysql-grammar.php
python3 ms/orbita-db/tests/csv-profile.py /Users/Shared/SharedProject/БД/orbitadb-csv
python3 scripts/check-migrations.py
```

Первый тест использует только синтетические записи в SQLite `:memory:` и не читает `.env`: 50 таблиц, порядок колонок, неуникальные morph indexes, nullable parents, реальные Eloquent morphMany/morphTo, одинаковые ID разных типов родителей, проверка коллизии до DDL, rollback/reapply и сохранность служебной таблицы. Второй компилирует MySQL DDL с запретом реального подключения. Проверка CSV сопоставляет ширину всех 8 043 строк с manifest, не печатает значения ячеек.

Исполнение на MySQL-сервере и импорт данных не проверены. Для этих шагов потребуется отдельная тестовая база.
