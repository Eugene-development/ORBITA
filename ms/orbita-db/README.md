# ORBITA DB — отдельный локальный Laravel-сервис

Восстановленная структура находится в `database/recovery/2026_10_14_000000_reconstruct_legacy_schema.php`.
Это отдельный, явно запускаемый набор Laravel migrations для новой базы после потери старой. Он создаёт 50 таблиц. Обычные служебные миграции `orbita_*` остаются в `database/migrations`, без изменений. Сервис имеет собственные `artisan`, `composer.json`, `composer.lock`, `bootstrap`, `config`, команды импорта и тесты. API и его vendor для запуска не нужны.

## Локальный runtime и SSH-туннель

Миграции и импорт выполняются **локальным PHP на Mac из этой папки**, не на VPS и не из Docker-образа. Основная инструкция: [VPS/18 — подключение к БД с локальной машины](../../../VPS/18-local-database.md). Laravel 13, PHP 8.4+ с PDO MySQL/mbstring и Composer. HTTP-сервер, Redis, Node и Docker для этого сервиса не нужны.

```sh
# Mac: перейти в самостоятельный сервис и установить его зависимости.
cd /Users/Shared/SharedProject/Development/ORBITA/ms/orbita-db
composer install
```

При первой настройке скопировать `.env.example` в `.env`, заполнить DB_DATABASE, DB_USERNAME и DB_PASSWORD миграционного пользователя своей базы. Существующую `.env` не перезаписывать. База этого проекта — `leget_orbita`, миграционный пользователь — `orbita_migrate`; обычный API на VPS использует отдельного пользователя без DDL. Локальные доступы никогда не копируются в `prod/orbita-api` или образы.

```dotenv
APP_ENV=production
APP_DEBUG=false
DB_CONNECTION=mysql
DB_HOST=mysql
DB_PORT=13306
DB_DATABASE=leget_orbita
DB_USERNAME=leget_orbita_migrate
DB_PASSWORD="REPLACE_MIGRATION_PASSWORD"
MYSQL_ATTR_SSL_CA=cert/mysql-ca.pem
ORBITA_CATALOG_WRITES_ENABLED=false
```

Сохранить публичный CA с VPS локально (закрытые ключи не копировать):

```sh
mkdir -p cert
scp root@185.4.66.102:/root/Project/Infrastructure/tls/ca.pem cert/mysql-ca.pem
openssl x509 -in cert/mysql-ca.pem -noout -subject -issuer -dates
chmod 600 .env
```

В локальном `/etc/hosts` должна быть запись `127.0.0.1 mysql`, как в VPS/18. `DB_HOST=mysql` сохраняет проверку имени TLS-сертификата; не заменять его на IP и не отключать проверку сертификата. Относительный путь CA разрешается от корня `orbita-db`; абсолютный тоже поддерживается. `DB_URL` не используется и не может переопределить эти настройки.

В отдельной вкладке терминала Mac открыть туннель и оставить вкладку работающей:

```sh
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:13306:172.30.50.2:3306 root@185.4.66.102
```

Это параметры действующего сервера из VPS/18; если адрес или Docker-сеть менялись, сначала проверить внутренний адрес MySQL по той инструкции. Туннель использует SSH-доступ к VPS, Laravel — отдельный MySQL-пароль мигратора.

Во второй вкладке, в `ms/orbita-db`, проверить соединение:

```sh
lsof -nP -iTCP:13306 -sTCP:LISTEN
php artisan config:clear
php artisan orbita:connection-check
php artisan migrate:status
```

`orbita:connection-check` читает имя выбранной базы и TLS cipher без изменения данных. На новой пустой базе `migrate:status` ожидаемо сообщит об отсутствии `orbita_migrations`.

Далее выполняйте основной процесс по порядку: **восстановление таблиц → импорт CSV → служебные миграции**. Команды служебных миграций находятся после раздела импорта CSV.

Архив `MAIN-DB-2023` использует UUID и не соответствует числовым ID выгрузки. Использована более ранняя версия `MAIN-DB`. Миграция самодостаточна и не требует этих архивных директорий при запуске.

`database/recovery-manifest.json` фиксирует источник, порядок колонок и наличие CSV для каждой таблицы. Для пустых и отсутствующих CSV схема восстановлена по архиву. Это реконструкция, а не подтверждённый schema-only экспорт production.

## Связи и принятые решения

- Имена таблиц сохранены, преимущественно в единственном числе.
- Числовые `id` с автоинкрементом сохранены по архиву: unsigned integer для сущностей, unsigned bigint для системных таблиц. Это глобальный ID таблицы, не отдельная последовательность на каждый `key`.
- `parentable_type` (nullable string) + `parentable_id` (nullable unsigned bigint) создаются явно через `nullableNumericMorphs`, независимо от глобальных UUID-настроек Laravel. Составной индекс не уникален: один родитель может иметь множество дочерних записей. Внешний ключ на одну таблицу здесь невозможен.
- Для таблиц с `key` и полиморфным родителем добавлен неуникальный индекс `(key, parentable_type, parentable_id)` под запросы проекта.
- `key` — строка длиной 36, совместимая со старым MySQL `uuid`/CHAR(36). В CSV встречаются `1` и `2`; оба сохраняются. Default изменён с архивного `base` на `1` для текущего проекта. Это осознанное решение реконструкции, не доказанный старый default. У таблицы `key` нет одноимённой колонки согласно архиву.
- `price.value` — `DECIMAL(20,2)` вместо архивного INTEGER: все выгруженные цены целые (0–400222432), а текущий код поддерживает копейки. Float/double не используются. Это осознанное расширение схемы.
- Nullable timestamps, deleted_at, поля slug/hash/alt и особые структуры `users`, `cart`, `jobs`, токенов сохранены по архиву. Cart не превращается в полиморфную таблицу: архив содержит product_id и session_user.
- На slug и полиморфные пары не добавлены уникальные ограничения. Наличие `morphOne` в некоторых моделях не доказывает уникальность данных; миграция не мешает восстановить несколько дочерних строк.
- Типы в CSV — короткие morph aliases (`product`, `category` и т. д.). При импорте их нельзя заменять PHP-именами классов. Morph map настраивается приложением, не DDL.

CSV отсутствуют для `users`, `unit`, `text`, `team`, `title`, `service`, `seotitle`, `video`, `tag`, `visit`, `technology`. Их таблицы создаются пустыми. Пустые `menu`/`project` и отсутствующие другие родители означают, что создание схемы само по себе не восстановит целостность каталога. `taggables` и `action` из более позднего архива не включены: их нет ни в журнале этой базы, ни в CSV.

## Запуск на новой базе

Все следующие команды выполняются локально в `ms/orbita-db` с его собственной `.env`, пока SSH-туннель открыт.

1. Настроить локальное подключение `orbita-db` через туннель к вашей чистой целевой MySQL-базе с её обычным именем. Восстановление выполняется сразу в неё; промежуточная база и последующий перенос не нужны. Проверить DB_DATABASE и очистить кэш конфигурации командой `php artisan config:clear`.
2. Из `ms/orbita-db` выполнить:

```sh
php artisan migrate --path=database/recovery
```

3. После успешного создания таблиц перейти к разделу «Формат CSV и импорт данных» ниже и загрузить CSV. Служебные таблицы приложения создаются после успешного импорта, в отдельном заключительном шаге.

Artisan сервиса `orbita-db` использует собственную настройку журнала `orbita_migrations`. Таблица `migrations`, создаваемая восстановлением, предназначена только для старого журнала. Не переключать Laravel на этот старый журнал и не выдавать его содержимое за историю новых миграций.

Перед первым CREATE проверяется отсутствие **всех** 50 целевых таблиц. Если любая уже существует, восстановление останавливается, ничего не создавая. MySQL DDL не атомарен: при ошибке посередине останется частичная схема; повторный запуск откажет, и нужно разобраться с причиной на отдельной новой базе. `down()` удаляет только эти 50 legacy-таблиц в обратном порядке и уничтожает их данные; служебные `orbita_*` не затрагивает.

Миграция создаёт только структуру: не импортирует CSV, не создаёт фиктивные товары/родителей, не включает каталоговые записи и не устанавливает schema approval. Запуск на реальной базе в рамках подготовки не выполнялся.

## Формат CSV и импорт данных

Файлы без заголовков: первая строка — данные. Порядок колонок указан в manifest. Это CSV с обратной косой чертой для экранирования кавычек; стандартное чтение без этого параметра ошибочно разбивает 164 строки product. SQL NULL представлен некавыченным `\N`.

Команда `orbita:recovery-import` находится только в `orbita-db` и читает локальный `database/recovery-manifest.json`. Команды API и Docker-образы не участвуют.

Из `ms/orbita-db` сначала выполнить проверку только файлов (без подключения к БД):

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv --dry-run
```

В исходном `image.csv` было 2 082 записи и 17 конфликтов ID. По решению пользователя 20.10.2026 удалены **17 повторных строк**, первые записи каждого ID оставлены без изменений. Сейчас в файле **2 065 изображений**, дубликатов ID нет. Проверенная резервная копия исходного файла сохранена вне папки импорта: `/Users/Shared/SharedProject/БД/orbitadb-csv-backups/image-before-id-cleanup-20261020-f1915b419cfb.csv.bak`. В manifest обновлено количество строк и сохранены исходный счётчик и число удалённых повторов.

Для текущей очищенной выгрузки перенумерация ID не нужна. Проверка:

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv \
  --dry-run > /tmp/orbita-recovery-plan.txt
```

Для данной выгрузки подготовлены 8 007 строк: 7 958 записей каталога и 49 записей архивного журнала `migrations`. 19 строк `password_resets` пропускаются. Команда всегда исключает `password_resets`, `personal_access_tokens`, `jobs`, `failed_jobs`, `cart`: старые токены, очередь и сессии не восстанавливаются. Исходные CSV и их значения в репозиторий не копируются.

Дополнительная опция `--reassign-conflicting-image-ids` остаётся доступной для других проверенных выгрузок с соответствующим manifest: первая запись сохраняет ID, повторные получают номера выше максимального исходного ID image, с отчётом `id_reassignments`. ID, на которые уже ссылаются строки CSV, пропускаются. При ссылках на конфликтующий ID, неизвестных morph aliases или исчерпании диапазона перенумерация отказывает. Конфликты ID других таблиц не разрешает. **Для текущих очищенных CSV эта опция не требуется.**

### Проверка подключения и загрузка

1. Настроить локальное подключение `orbita-db` через открытый SSH-туннель к вашей чистой целевой MySQL 8.0+/8.4 базе с любым именем и выполнить recovery-миграцию по инструкции выше. Это та же база, которую затем будет использовать приложение; промежуточный перенос не требуется. Все другие процессы записи/очереди должны быть остановлены; `ORBITA_CATALOG_WRITES_ENABLED=false`. Проверить `DB_DATABASE` и кэш конфигурации. Импортёр не создаёт базу/таблицы и не переключает подключение.
2. Проверить CSV и целевую схему без вставок, явно указав её точное имя (`leget_orbita`):

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv \
  --dry-run --target-database=leget_orbita
```

3. После просмотра отчёта выполнить загрузку теми же параметрами без `--dry-run` и сохранить отчёт импорта:

```sh
php artisan orbita:recovery-import /Users/Shared/SharedProject/БД/orbitadb-csv \
  --target-database=leget_orbita > /tmp/orbita-recovery-import.txt
```

`--target-database` — проверка точного имени настроенной и реально подключённой базы, а не переключатель подключения. Для этого проекта имя базы — `leget_orbita`; обязательного префикса у импортёра нет. Импорт выполняется непосредственно в неё. Префикс таблиц в настройках подключения должен быть пустым. SQLite `:memory:` доступен исключительно тестам.

Перед вставкой проверяются все 50 таблиц, порядок колонок, отсутствие FK/представлений/триггеров, независимый auto-increment ID и InnoDB. Все legacy-таблицы должны быть пустыми; необязательные `orbita_*` service-таблицы тоже, кроме журнала `orbita_migrations`. Неизвестные таблицы запрещены. Нужен строгий SQL mode. Импортёр не дописывает, не заменяет, не чистит таблицы и не вызывает Eloquent events, сидеры или старые миграции.

CSV целиком проверяются до первой вставки: наличие всех ожидаемых файлов, точное количество строк из manifest, ширина строк, UTF-8, формат ID/дат/Decimal. Файлы без CSV по manifest остаются отсутствующими; неожиданно найденные файлы требуют предварительного пересмотра manifest. Снимок ограничен 32 MiB и 100 000 строк, CSV-симлинки запрещены. После разбора используется неизменяемый снимок в памяти; файлы не перечитываются во время загрузки. Отчёт содержит SHA-256 каждого файла и только служебные данные — без текстов товаров, email, токенов и SQL bindings.

Вставки выполняются пакетами в **одной транзакции**. Advisory lock исключает одновременный запуск другого recovery-импортёра; он не заменяет остановку внешних писателей. Ошибка вставки, предупреждение конвертации MySQL или несовпадение количества строк/MAX(id)/AUTO_INCREMENT откатывают все вставленные строки. Счётчики InnoDB могут продвинуться даже после rollback; команда проверяет следующий ID выше максимального восстановленного, не выполняя ALTER TABLE. Повторный успешный импорт запрещён из-за непустых таблиц.

`relationship_issues` содержит количество отсутствующих/неполных/неизвестных родителей, межпроектных ссылок, групп повторяющихся slug и неоднозначных morphOne-связей. Эти строки сохраняются как в выгрузке. На текущем снимке найдены 374 отсутствующих родителя, 1 неполная и 1 межпроектная связь, 15 групп повторяющихся slug товаров; их исправление — отдельная работа. Успешный импорт не означает целостный каталог: approval и обычные записи приложения остаются выключенными. Общий allocator впоследствии инициализируется штатной проверкой/утверждением схемы; импортёр его не обходит для работающего приложения и не создаёт approval.

`csv-profile.py` остаётся отдельной проверкой числа полей, а не импортёром.

## Служебные миграции — после импорта CSV

**Выполнять после успешного восстановления таблиц и загрузки CSV.** Это заключительный шаг подготовки базы: он создаёт служебные таблицы приложения — сотрудников, заказов, платежей и другие `orbita_*` таблицы.

Все команды по-прежнему выполняются локально из `ms/orbita-db`, пока SSH-туннель открыт. Сначала посмотреть SQL:

```sh
php artisan orbita:service-migrate --pretend
```

Если предварительный просмотр завершился без ошибок, применить миграции:

```sh
php artisan orbita:service-migrate
```

На запрос подтверждения Laravel выбрать **Yes**. Команда запускает стандартный `migrate` из `database/migrations` и сверяет структуру всех несервисных таблиц/представлений/триггеров до и после. Повторный запуск пропускает уже применённые миграции. Schema approval и запись в каталог этот шаг не включает. `--force` используется только для заранее проверенного неинтерактивного запуска.

Папка `orbita-db` не собирается и не публикуется как Docker-образ. В Compose нет migration-сервиса. Скрипт из корня `bash scripts/migrate-services.sh production` — локальная оболочка для этой же команды, без Docker/SSH-запуска команд. Туннель открывается отдельно. API/VPS start/update только читают статус через `orbita:migrations-check`, не имеют миграционных доступов и не выполняют DDL.

## Проверки

Из корня ORBITA, при установленных зависимостях `orbita-db`:

```sh
php ms/orbita-db/tests/recovery.php
php ms/orbita-db/tests/mysql-grammar.php
python3 ms/orbita-db/tests/csv-profile.py /Users/Shared/SharedProject/БД/orbitadb-csv
python3 scripts/check-migrations.py
composer --working-dir=ms/orbita-db test
```

Первый тест использует только синтетические записи в SQLite `:memory:` и не читает `.env`: 50 таблиц, порядок колонок, неуникальные morph indexes, nullable parents, реальные Eloquent morphMany/morphTo, одинаковые ID разных типов родителей, проверка коллизии до DDL, rollback/reapply и сохранность служебной таблицы. Второй компилирует MySQL DDL с запретом реального подключения. Проверка CSV сопоставляет ширину всех 8 026 строк очищенной выгрузки с manifest, не печатает значения ячеек.

`RecoveryImportTest` проверяет синтетические CSV и SQLite `:memory:`: NULL/пустые строки/escaping, повреждённые файлы, Decimal/даты/ID, отчёт по связям, перенумерацию image и запрет неоднозначных ссылок, пустую схему, повторный импорт, позднюю ошибку и rollback, отсутствие секретов в ошибках, регистрацию команды и dry-run без запросов к БД.

`tests/import-mysql.php` дополнительно проверен на отдельном временном MySQL 8.4: атомарный rollback после ранних успешных вставок, точные Decimal/текст/NULL/key, перенумерация image, AUTO_INCREMENT, отказ от повторного импорта и не-InnoDB. Скрипт использует только синтетические CSV, не читает `.env`, создаёт и удаляет собственную базу со случайным именем `orbita_test_csv_*` (без префикса `orbita_recovery_`), проверяя прямой импорт и отказ при несовпадении целевого имени. Запускать только с одноразовым локальным MySQL на отдельном loopback-порту, указав `ORBITA_RECOVERY_MYSQL_TESTS=1` и `ORBITA_RECOVERY_MYSQL_TEST_PORT`. Сам тест исполняется локальным PHP и использует только `orbita-db/vendor`:

```sh
ORBITA_RECOVERY_MYSQL_TESTS=1 ORBITA_RECOVERY_MYSQL_TEST_PORT=13307 php ms/orbita-db/tests/import-mysql.php
```

Порт примера должен вести только к одноразовому синтетическому MySQL, не к VPS. Скрипт не открывает туннель и не читает `.env`. Импорт реальных CSV в MySQL в рамках разработки не выполнялся; очищенные CSV проверены файловым dry-run без перенумерации image.

## Необязательная локальная dev-БД

Этот раздел относится к изолированной dev-БД из `docker/local`, а не к восстановлению `leget_orbita` на VPS. Скопировать `.env.local.example` в `.env.local`, задать её локальные DB-доступы и использовать `php artisan --env=local migrate` либо `bash scripts/migrate-services.sh local` из корня. В этом профиле MySQL доступен на `127.0.0.1:4153`; это локальная тестовая БД, не туннель к VPS. Пустой CA разрешён только для этого изолированного сценария по явной конфигурации.
