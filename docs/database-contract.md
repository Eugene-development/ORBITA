# Контракт существующего каталога

## Неизменяемая часть

Каталоговые таблицы, их колонки/индексы/ограничения, существующие ID и значения цены не изменяются переносом. Точное устройство many-to-many пока не подтверждено: старый код описывает полиморфные связи, а реальные pivots определит экспорт. Любые дополнительные mapping changes выполняются по подтверждённому снимку, без DDL и очистки данных.

Нужен schema-only экспорт с CREATE TABLE, индексами, FK, views и triggers, без выбора другой БД и account statements. Дополнительный неперсональный отчёт: версия MySQL/MariaDB, engines, `key`, morph aliases, MAX(id), дубли morphOne и slug. В `database/schema` сохраняются локальные оригиналы экспорта; они исключены из Git и Docker image.

## Локальное восстановление

`scripts/import-local.sh` автоматически принимает только table-DDL: CREATE/ALTER/DROP TABLE, индексы и FK внутри этих определений, допустимые session SET из mysqldump. Он отклоняет данные, account statements, выбор другой базы, views, triggers и DELIMITER.

Сохранить полный экспорт без потери исходных определений, а для первого импорта предоставить отдельный файл с таблицами. Views и triggers не удалять из оригинала и не считать автоматически перенесёнными. Их определения и зависимости проверяются после получения реального экспорта; восстановление выполняется отдельно только в изолированном клоне. Затем их метаданные и влияние на запись проверяются через `orbita:catalog-inspect` и тесты. Неизвестные объекты продолжают закрывать gate до добавления подтверждённых mappings/allowlists.

## Включение записи

1. Сохранить полный исходный экспорт. Импортировать проверенный table-DDL в изолированную БД с тем же engine/version. Если в экспорте присутствуют views или triggers, отдельно проверить и восстановить их до проверки совместимости; без этого клон не считается эквивалентным production. Создать разрешённые синтетические записи.
2. `orbita:catalog-inspect` выдаёт metadata, проблемы и fingerprint; неизвестные aliases/нетранзакционные таблицы/неоднозначные связи не исправляются автоматически.
3. Применить только служебные миграции. Остановить несовместимых writers; перевести все приложения/импортеры на LegacyIdAllocator.
4. `orbita:catalog-approve FINGERPRINT --writers-coordinated` сохраняет согласование и инициализирует счётчики по глобальному MAX каждой физической таблицы.
5. Установить `ORBITA_SCHEMA_FINGERPRINT`, `ORBITA_WRITERS_COORDINATED=true`, `ORBITA_CATALOG_WRITES_ENABLED=true`. Сам по себе env-флаг без записанного согласования и совпадения metadata не открывает CRUD.

Счётчик общий для всех project keys. Price ID не равен Product ID. Все счётчики блокируются в одном порядке; записи связаны фактическим product ID и сохранённым alias. При ошибке транзакция откатывает карточку и счётчики.

Удаление — отключение `is_active`; shared objects и ссылки других сущностей не удаляются. Существующие журналы `data-imports` — история прежних операций, а не seed-файлы.

## Откат

Служебные таблицы, allocator и историю платежей сохранять. Старый writer с `MAX(id)+1` нельзя включать параллельно с новым allocator. Откат приложения допускается на совместимую версию либо при остановленной записи.
