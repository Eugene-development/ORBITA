# Laravel: production-поставка ORBITA

Обновлено 22.10.2026 после проверки запуска LEGET. Эта инструкция заменяет прежние
указания о серверных миграциях, генерации ключей при старте и включении .env в образ.

| Исходники | Серверная папка |
| --- | --- |
| `ms/orbita-api` | `prod/orbita-api` |

## Настройки перед сборкой и запуском

`.env` исходников не включается в Docker-образ. В каждой серверной папке создайте
`.env` из `.env.example` и установите права 600. `DB_HOST=mysql`, `DB_PORT=3306`,
`DB_NETWORK=leget-db` соответствуют действующему VPS. Имена `DB_DATABASE`,
`DB_USERNAME` и пароль берите из реально созданных аккаунтов именно этого проекта;
поля оставлены пустыми, чтобы случайное примерное имя не вызвало Access denied.
Не используйте доступы LEGET или локальный migration-аккаунт для другого проекта.

Сохраните существующий APP_KEY каждого сервиса; не заменяйте его ключом другого проекта.
Значение ключа начинается с `base64:`, без повторного `APP_KEY=`. При переносе
сохраните ключ из работающего приложения/backup. Ранее некоторые entrypoint
генерировали ключ при каждом старте: локальный ключ не гарантированно совпадает
с тем, которым зашифрованы серверные данные. Новые ключи не генерируются автоматически.
Entry point проверяет длину ключа и обязательные DB-поля без раскрытия секретов.

Публичный CA `cert/mysql-ca.pem` находится в корне каждого исходного сервиса
в каталоге `cert/` и включается в образ; отдельный mount/доставка на VPS не нужны.
Укажите `MYSQL_ATTR_SSL_CA=cert/mysql-ca.pem`. Проверка TLS не отключается.
SMTP, Object Storage, платежи и прочие интеграции настройте для своего проекта.
Существующие JWT secrets сохраняйте; они должны совпадать у взаимодействующих сервисов.

## Миграции

Канонические миграции находятся в `ms/orbita-db`. Выполняйте их только PHP
с локальной машины через SSH-туннель по `Development/VPS/18-local-database.md`.
На VPS и в production-образах миграторов нет. Подготовка схемы не запускается
автоматически при старте приложения. Доступы мигратора остаются только локально.

## Выпуск и проверка

Пересоберите backend-образы штатными deploy-скриптами, затем доставьте актуальные
Compose, scripts и заполненные `.env`. Сохраните существующие секреты и данные.
Из каждой серверной папки выполните `./scripts/update.sh`: pull и пересоздание
контейнеров. Для изменения только `.env`: `docker compose up -d --force-recreate`.
Обычный restart не перечитывает env_file.

`APP_ENV=production`, `APP_DEBUG=false`, `LOG_CHANNEL=stderr` позволяют искать
ошибки через `docker compose logs --since 5m app` (имя app смотрите в Compose).
Сначала проверьте health endpoint на опубликованном loopback-порту, затем SQL/TLS
из приложения. HTTP 200 health не гарантирует доступ к БД. Ошибки шифрования,
SQLSTATE 1045 и таймауты требуют разных исправлений — смотрите свежую запись лога.

Постоянные volumes с данными сохраняются. Старые cache/public volumes больше
не перекрывают код образа; эти volumes автоматически не удаляются.

Защита ORBITA сохранена: read-only root, UID 82, tmpfs, проверка fingerprint и координации writers, запрет записи в каталог до подтверждения. Backup-клиент берёт публичный CA из `ms/orbita-api/cert/mysql-ca.pem`; runtime получает его из образа.
